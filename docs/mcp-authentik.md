# Connect MCP clients through Authentik

## Built-in OAuth broker

Enable the broker by setting `auth.mcpBrokerKeyEnv` to the name of a secret environment variable containing 32 random bytes encoded in standard base64. Use the same value on both replicas and keep Redis state shared. The chart consumes the existing credential Secret. Keep the browser OIDC application with its existing `/auth/callback` and `groups` mapping. The broker reuses that sign-in and asks for a separate MCP consent. Authentik needs no callback from individual MCP clients.

In a client that supports remote HTTP and MCP OAuth discovery, add the `/mcp` endpoint URL. The broker uses public Authorization Code clients with S256 PKCE, accepts HTTPS and native HTTP loopback redirects, and enforces exact redirect matching apart from the loopback port. It supports Client ID Metadata Documents over public HTTPS and stateless Dynamic Client Registration for older clients. The issuer is `/mcp/auth` on the configured public origin. Its tokens work only on that origin's `/mcp` resource. An explicit request for a different resource is rejected. Clients that omit the indicator use the issuer's sole MCP resource.

Consent starts with read access when the client requested it. A user must explicitly grant write or delete, and the user's existing source roles still apply. Public clients that declare refresh support receive rotating refresh tokens. A grant lasts at most `auth.sessionTtl` and also ends when its originating web session ends. Use the broker's revocation endpoint to end an individual grant. A reused refresh token revokes its grant.

If a deployment cannot reach some public client metadata documents, run `cdn-manager serve-mcp-metadata` on a trusted egress network. Set `CDN_MANAGER_METADATA_RELAY_LISTEN` to its private overlay address and port, and `CDN_MANAGER_METADATA_RELAY_TOKEN` to a secret containing 32 random bytes in unpadded base64url. Configure `auth.mcpMetadataRelayUrl` with the relay's `/v1/client-metadata` endpoint and `auth.mcpMetadataRelayTokenEnv` with the name of the matching secret environment variable. Plain HTTP is for a private encrypted overlay or loopback. Other deployments must use HTTPS. The broker tries direct fetches first, and the relay applies the same public-address and document checks. Authentik still handles sign-in through the existing web application.

The broker is opt-in. Before switching in production, verify clean Codex, VS Code and Inspector profiles with an endpoint-only configuration against a staged instance. Use the same browser OIDC subject and roles as the existing installation. Retain the previous `mcpIssuer` and `mcpAudience` values for rollback by clearing `mcpBrokerKeyEnv`. Existing external MCP tokens need reauthorization after switching. Once the rollout is verified, remove per-client Authentik callbacks and client overrides that were used for the external MCP provider.

## External OAuth provider

Use a dedicated Authentik OAuth2/OpenID provider and application for the MCP endpoint. The browser UI uses a separate confidential provider. Enable the Authorization Code grant explicitly on both providers. Set both providers to the same stable Subject Mode, such as hashed user ID, so the same user can resume an upload from either interface. Select an asymmetric signing key and enable inclusion of scope claims in tokens. [Authentik OAuth2 provider](https://docs.goauthentik.io/add-secure-apps/providers/oauth2/)

1. For the UI provider, register the exact HTTPS callback `https://manager.example.com/auth/callback`. The manager requests `openid profile`. Make sure the signed ID token contains `groups` as an array of strings, using a scope mapping on `profile`.
2. For the MCP provider, use a public client with Authorization Code and S256 PKCE. Register the exact Inspector callback `http://127.0.0.1:6276/oauth/callback`. Bind the application to the intended user groups. Create a `read` scope mapping that returns the `groups` claim in the signed access token. Add `write` and `delete` mappings only when those MCP operations are needed. Restrict sensitive scopes with an Authentik application policy as appropriate. [Authentik scope mappings](https://docs.goauthentik.io/add-secure-apps/providers/property-mappings/)
3. In the manager configuration, set `auth.mcpIssuer` to the MCP provider's issuer exactly as advertised in its OIDC discovery document, including any trailing slash. Set `auth.mcpAudience` to the dedicated MCP client ID that Authentik puts in `aud`. List enabled scopes in `auth.mcpScopes`, for example `["read", "write"]`. `auth.publicUrl` supplies the MCP resource URL and callback origin. [MCP audience binding](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization#token-handling)

Open **MCP Settings** in CDN Manager to copy the command for your installation. Run Inspector in a terminal with its pre-registered client ID and sign in through the browser using the same account as in CDN Manager. Inspector handles the OAuth exchange automatically. The CLI needs a Node.js version supported by Inspector. The example uses the current MCP protocol with HTTP scope challenges. [MCP Inspector authorization walkthrough](https://modelcontextprotocol.io/docs/tutorials/security/authorization)

```bash
npx @modelcontextprotocol/inspector@2.16.0 --cli https://manager.example.com/mcp \
  --transport http --protocol-era modern --client-id example-cdn-mcp \
  --method tools/call --tool-name list_sources
```

Compare the listed sources to the UI for the same Authentik account. `get_cdn_url` takes `source`, `bucket`, and `key`. Its `url` should match the permanent URL shown by the UI. A client holding only `read` receives an `insufficient_scope` challenge when it requests a write operation. Even after obtaining `write`, the account needs an editor or admin role for the source. `delete_object` also requires the `delete` scope and an admin role. Source grants may differ between sources.

The Inspector command was exercised with Authentik 2026.8.7, Inspector 2.16.0, and Node.js 24.22.1 on Ubuntu WSL2. Run it in a terminal so Inspector can prompt for the browser handoff. The local test used explicit loopback HTTP configuration. The example above uses HTTPS for the manager.

Use `start_upload` with the target `source`, `bucket`, `key`, and byte `size`, then call `grant_upload_part` with the returned `id` and a part `number`. Send that part as a raw body to the returned URL with `PUT` and the exact `Authorization` and `Content-Length` values from the result. Treat the authorization value as a credential and keep it out of command history and logs. It can retry the same part until expiry, at most five minutes. If it expires, request a new grant. Run `upload_status` after reconnecting and `complete_upload` once all parts are present. In Redis mode, a manager restart preserves existing browser sessions and grants until their original expiry. Standalone file mode keeps them in memory, so after a restart sign in again and request a new grant for the same durable upload session ID.

If authentication fails, inspect the actual provider's discovery metadata for `S256` in `code_challenge_methods_supported`. Compare the returned access token's issuer and audience to the manager configuration and verify that it contains the expected `scope` and `groups` claims. Use `--relogin` when changing Inspector's cached authentication settings. Include those checks in first-use acceptance with the selected Authentik version and client.
